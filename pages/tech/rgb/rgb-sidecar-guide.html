RGB 协议与 sidecar 方案

在已了解 Chain33 BTC 跨链桥的基础上，导读 RGB 协议怎么运作、以及为什么用一个 Rust sidecar 来做跨链集成。

对象：桥团队成员 阅读时长：约 8 分钟 状态：方案导读
01 · 一句话总结

RGB 是一种“把资产账本搬下链”的方案：比特币链上只存一个极小的“承诺”（指纹），真正的资产账本在参与者的软件里各自维护、互相验证。我们要做的跨链桥，本质是“帮 Chain33 学会验证 RGB 的账本”——而这个验证逻辑在 Rust 生态里最成熟，所以用一个 Rust 小进程（sidecar）专门干这件事。

02 · RGB 协议到底是什么

一个常见理解：seal UTXO 确实是最核心的

对 RGB 的一个常见印象是“RGB 就是一个 seal UTXO”，这个印象方向正确。在 RGB 里，资产的所有权确实锚定在一个比特币 UTXO 上——这个 UTXO 叫 seal（封印）：谁能花它，谁就拥有它封住的那笔资产；转账 = 花掉旧 seal、产生新 seal 落在收款人那里，资产跟着“搬家”。

但 seal UTXO 只是冰山一角。RGB 真正的难点在下面三点。

核心思想：资产账本不在链上

资产账本 = 一份“私人的账本”，放在参与者的软件里；比特币只负责“盖章”（存一个哈希指纹），证明“账本的这次变动和某一笔链上交易是绑定的”。

打个比方：比特币是一条大马路，人人都看得见；RGB 资产是马路两旁仓库里的存货——存货账本各自保管。每次存货变化，仓库主人在马路边贴一个指纹（哈希承诺），和某笔链上交易绑在一起；别人要看存货账对不对，需要把账本（consignment）给他看，他用指纹验证账本没问题。

这就是客户端验证（client-side validation）：资产真伪由参与的各方软件验证，而不是由比特币矿工验证。

三个关键词，讲透 RGB

概念白话技术名
seal（封印）一个装着“某笔资产所有权”的比特币 UTXO；谁能花它，谁拥有资产single-use seal
承诺贴进比特币交易里的“指纹”。两种贴法：OP_RETURN（opret，简单）或 Taproot 脚本（tapret，更强）opret / tapret commitment
状态转移 + consignment转账时钱包生成“文档”：从 seal A 转 X 个币到 seal B，跑一遍合约规则确认合法；指纹贴链上，全文直接发给对方state transition / consignment

合约与 Schema：资产不是随便发的

RGB 资产由一份合约定义，合约里的 Schema（模板）规定这类资产怎么运转：RGB20（IFA） 是同质化代币（如 USDT，固定精度、可增发）；UDA 是 NFT。每次转账，软件要执行 Schema 里定义的逻辑来校验——这个“执行逻辑”在 AluVM 虚拟机里跑，数据用 strict_types 编码。这两样加上校验规则本身，构成 RGB 的共识层——也是整件事最复杂、最难写对的部分。

所以，“光看链上”为什么看不到 RGB 资产

因为资产账本根本不在链上，链上只有一个哈希指纹。任何普通比特币浏览器上都看不到“某某地址有 1000 USDT”。要看，必须：拿到转账的 consignment，再用软件验证（跑 Schema 逻辑、核对 seal 链、核对链上指纹对得上）。

这也是对我们跨链桥最大的影响：充值进桥的钱，光靠“看比特币区块”认不出来，必须“收到 consignment + 跑验证”才能确认。

03 · 为什么需要 Rust sidecar

集成 RGB = 学会验证链下数据

我们现有的 BTC 桥是链上验证（看区块、验 SPV）。RGB 完全不同——它是链下验证：充值要收到用户的 consignment、跑客户端验证；提现要构造合法的状态转移（走 AluVM 执行、strict_types 编码）、锚进一笔比特币交易。而共识验证是最不能写错的东西——写错一点，就可能凭空铸造出没有实打实资产支撑的币，或把用户的钱卡住。

RGB 生态没有 Go 库

整个 RGB 生态的参考实现都是 Rust（共识、虚拟机、编码全是）。Go 生态没有现成可用的库。自己用 Go 从零写 = 约 1.5~2.5 万行，还要冒“和官方实现不一致”的共识风险。

为什么不直接用现成的 RLN？

我们认真评估过现成的 RLN（RGB Lightning Node）——Go 直接调它的 HTTP 接口，零 Rust 代码。但放弃了，三个硬伤：自持密钥（绕开 TSS 门限签名托管）、alpha 软件（官方声明不对资金损失负责）、官方只支持测试网（mainnet 要自己改代码）。

所以：自己写一个小的 Rust sidecar

sidecar = 一个独立的小 Rust 进程，专门负责“RGB 共识”：持有零私钥（watch-only，只看不签，所有签名都在 TSS 门限组）；对 Go 桥暴露 gRPC 接口（帮我验证这个 consignment / 帮我构造这笔提现）。就像一个“翻译官”：Go 说 Chain33 的话，Rust 说 RGB 的话， sidecar 在中间做翻译和校验。

04 · 一个关键约束：TSS → 单脚本钱包

这里是我们方案里最特别、也最容易踩坑的一点。我们的托管底座是 TSS 门限签名（5 个节点凑够 3 个才能签名），而 TSS 组只有一个公钥，没法派生出一堆不同的子地址（没有 BIP32 的 chain code）。

但 RGB 生态的库习惯是每笔交易生成一个新地址（BIP32 派生）。如果 sidecar 用了“派生地址”，资产落在派生地址上，TSS 组签不了。

所以 sidecar 被“逼”成特殊形态：单脚本钱包——所有地址都锁死成 TSS 那一个 P2WPKH 脚本，零派生。

这是整个方案的 make-or-break 点。Spike 1 已验证通过：wpkh(TSS公钥) 描述符能建出零派生的 watch-only 钱包，所有 seal 都落在 TSS 脚本上，TSS 能签。

05 · 整体架构 
用户(RGB钱包)          Bitcoin 链           sidecar(Rust, watch-only)     Go 桥(neutrino)        Chain33
    │ 付 invoice          │                       │                        │                    │
    ├──转账(带承诺)──────▶│───────────────────────▶│                        │                    │
    ├──交付consignment────┼───────────────────────▶│ 客户端验证              │                    │
    │                      │                       │ 确认资产到桥seal ──────▶│ 铸造 X.RGB20_USDT ─▶│
    │                      │                       │                        │                    │
    │◀──RGB转账到用户──────┼───────────────────────│◀──构造状态转移+PSBT─────│◀──用户发起提现─────│
    │                      │◀────广播已签交易──────│◀──TSS签名──────────────│                    │

一句话： sidecar 在中间，把“RGB 资产如何进出”翻译成 Go 桥能理解的操作；TSS 在底下把每一次花费都门限签名。

06 · 两条核心链路

充值（把 RGB 资产变成 Chain33 上的资产）

  1. 用户想要充值，桥发给他一个 RGB 收款单（invoice）（绑定某次充值请求）；
  2. 用户用 RGB 钱包付这个收款单——钱从用户的 seal 转到桥的 seal；
  3. 用户把 consignment 交给桥（上传或走 RGB 中转服务器）；
  4. sidecar验证 consignment：跑 Schema 逻辑、核对 seal 链、核对链上指纹，确认资产真的到了桥的 seal、金额正确；
  5. 确认无误后，Go 桥在 Chain33 上铸造等额的 X.RGB20_USDT 给用户。

提现（把 Chain33 资产变回 RGB 资产）

  1. 用户在 Chain33 发起提现，目标填他自己 RGB 钱包生成的 invoice；
  2. Go 桥把提现请求交给 sidecar；
  3. sidecar 构造状态转移 + 一笔未签名的比特币交易（PSBT）；
  4. TSS 门限组签名这笔交易的输入；
  5. 广播交易 → RGB 资产从桥的 seal 转到用户的 seal；
  6. Chain33 上销毁等额的 X.RGB20_USDT。
07 · 关键决策一览
决策为什么
用 Rust sidecar，不自己用 Go 写 RGBRGB 共识验证在 Rust 生态最成熟；Go 自写风险大、工作量大
不用现成 RLN它自持密钥（绕开 TSS）、alpha、不支持 mainnet
sidecar watch-only（零私钥）签名全部留在 TSS 门限组，安全底线不破
单脚本钱包（零派生）TSS 只有一个公钥，派生子地址签不了（Spike 1 已验证）
充值走 per-request invoiceRGB 收款必须预先建好 receive，且天然解决“这笔充值归谁”
提现走 PSBT 外部签名RGB 库构造交易，TSS 签名，两边各干各的、互不干扰
